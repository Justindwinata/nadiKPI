# NADI — Runtime Release-Host Bootstrap Contract

## Purpose

Production release verification must run on a host that can satisfy the same executable contract as CI. The repository therefore separates:

1. **source constraints** — `composer.json`, `package.json`, `requirements-e2e.txt`;
2. **release-host constraints** — `config/release-environment.json`;
3. **ephemeral gate credentials** — generated by `scripts/generate-release-gate-env.sh`;
4. **authoritative verification** — `scripts/final-gate.sh`.

No bootstrap helper can authorize `FINAL PASS`. Only the complete authoritative final gate can do that.

## Canonical constraints

`config/release-environment.json` records only host requirements that must stay explicit for release verification. The checker also asserts that duplicated constraints have not drifted from their canonical manifests:

```text
PHP requirement       composer.json#require.php
Node engine           package.json#engines.node
npm engine            package.json#engines.npm
Playwright version    requirements-e2e.txt
MySQL major           config/release-environment.json (8)
PHP extensions        config/release-environment.json
Composer major        config/release-environment.json
Python minimum        config/release-environment.json
```

Validate source alignment without touching a database:

```bash
python3 scripts/release_environment.py contract
```

## Verification database

Use an isolated **actual MySQL 8** database that may be destroyed, for example:

```text
nadi_test
nadi_ci
nadi_verification
```

Never point the gate at production data. The database name must contain an explicit `test`, `testing`, `ci`, `verify`, or `verification` scope token. `NADI_VERIFY_DESTRUCTIVE_DATABASE` must exactly equal `DB_DATABASE`.

Minimum connection variables:

```bash
export DB_CONNECTION=mysql
export DB_HOST=127.0.0.1
export DB_PORT=3306
export DB_DATABASE=nadi_verification
export DB_USERNAME='<verification user>'
export DB_PASSWORD='<verification password>'
```

The release-host doctor probes the server with PDO before dependency installation and requires the server major version to be `8`. MariaDB/SQLite are not accepted as substitutes for production release evidence.

## Ephemeral acceptance identities

Do not hand-maintain acceptance passwords. After `DB_DATABASE` has been set to a safe verification database, generate the non-production APP key, destructive acknowledgement, and acceptance identities from the repository helper.

For Bash/zsh:

```bash
source <(bash scripts/generate-release-gate-env.sh \
  --format shell \
  --database "$DB_DATABASE" \
  --run-id local-release)
```

The helper deliberately refuses a database name that is not test/CI/verify scoped. It does **not** generate or print the MySQL password.

For GitHub Actions the same helper writes GitHub environment-file syntax:

```bash
bash scripts/generate-release-gate-env.sh \
  --format github-env \
  --database "$DB_DATABASE" \
  --run-id "${GITHUB_RUN_ID}-${GITHUB_RUN_ATTEMPT}" \
  >> "$GITHUB_ENV"
```

Generated values are ephemeral and must not be committed.

## Toolchain bootstrap

Before running the gate, the host must provide:

- PHP satisfying `composer.json` plus the required extensions;
- Composer major version declared by the release-host contract;
- Node/npm satisfying `package.json`;
- Python satisfying the release-host contract;
- `pip install -r requirements-e2e.txt`;
- Playwright Chromium, or an explicitly managed Chromium executable through `NADI_BROWSER_EXECUTABLE_PATH`;
- `curl`, `unzip`, `cmp`, and SHA-256 tooling;
- reachable actual MySQL 8 verification database.

The repository intentionally does not run `sudo`, Homebrew, apt, or another system package manager automatically. System package installation is infrastructure-owned; the repository only verifies the resulting host deterministically.

## Readiness evidence

Run:

```bash
bash scripts/release-gate-doctor.sh
```

When invoked through `scripts/final-gate.sh`, phase `00-execution-readiness-doctor` writes:

```text
artifacts/release-gate/runtime_contract.json
artifacts/release-gate/runtime_environment.json
```

The environment evidence contains tool versions, extension presence, DB/MySQL status, browser status, and only **boolean presence** for required secret environment variables. Passwords, APP key bytes, and database password values are never serialized.

A failed doctor is a release-gate failure, not a production PASS. Correct the host or environment and rerun the full gate.

## CI parity

`.github/workflows/release-gates.yml` provisions MySQL 8.4, PHP 8.4 + required extensions + Composer v2, Node 22.12, Playwright, and Chromium. It uses the same credential generator and executes the same `scripts/final-gate.sh` used by local verification.

CI artifacts retain release-gate/browser evidence for diagnosis. They are excluded from the production package.

## Execution

After the host passes readiness:

```bash
bash scripts/final-gate.sh
```

Do not reuse `vendor`, `node_modules`, synthetic `public/build`, or a previous database state as proof. The authoritative gate deletes/recreates dependency/build state and performs guarded MySQL resets itself.
